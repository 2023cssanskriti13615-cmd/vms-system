# Smart Visitor Management & Secure QR Verification System

A web application that replaces the paper visitor book at an organisation's gate.
An employee invites a visitor by email, the visitor fills in their own details, a
single-use QR gate pass is issued, and security verifies that pass at the gate —
with the entry time written to the visitor register automatically.

Built with Python, Flask and SQLite.

---

## What the system does

| Role | What they can do |
|------|------------------|
| **Employee** | Sign in, invite a visitor, resend an invitation, view the full visitor register |
| **Visitor** | Open the emailed link, submit their details, receive a QR gate pass (no account needed) |
| **Security guard** | Sign in, scan the visitor's QR code with a phone camera, allow or refuse entry |

## How the security works

The invitation link and the QR code both carry a **token generated by Python's
`secrets` module** — 32 random bytes, URL-safe. A guessable identifier like
`/visitor/101` would let anyone walk through the visitor list by editing the
address bar; a random token cannot be guessed or enumerated.

At the gate the application performs three checks before showing a green screen:

1. Does the token exist in the database?
2. Has the visitor actually completed their registration?
3. Has this pass already been used for entry?

Once entry is approved, the record moves to `ENTERED` and the entry time is
stored, so the same QR code shown a second time returns **"Pass already used"**.
The check is repeated inside the approval request itself, so two simultaneous
scans still cannot both succeed.

Employee and guard pages are protected by session login, with passwords stored as
Werkzeug hashes — never as plain text.

## Database

A single `visitors` table carries one row per invitation, moving through four states:

`INVITED` → `REGISTERED` → `ENTERED` (or `REJECTED` at the gate)

| Column | Purpose |
|--------|---------|
| `token` | The random secret behind the QR code |
| `email`, `name`, `phone`, `company` | Visitor identity |
| `person_to_meet`, `unit`, `purpose` | Visit details |
| `visit_datetime` | When the visitor is expected |
| `status` | Current state of the pass |
| `created_at`, `registered_at`, `entry_time` | Audit trail |
| `verified_by`, `remarks` | Which officer decided, and why |

A separate `users` table holds the employee and guard accounts.

## Running it

Full instructions, including the Gmail App Password and the Render deployment, are
in **SETUP.md**. The short version:

```bash
pip install -r requirements.txt
cp .env.example .env        # then edit .env
python app.py               # http://127.0.0.1:5000
```

Default accounts (change these in `.env`):

- Employee — `employee` / `employee123`
- Guard — `guard` / `guard123`

## Current limitations

Worth stating honestly rather than overclaiming:

- The system needs network access for email delivery and for the visitor to open
  their link.
- Email delivery depends on the SMTP provider; a blocked or rate-limited account
  will stop invitations going out. The link is always shown on screen as a backup.
- The pass has no expiry time — it is invalidated by *use*, not by the clock.
- Visitor identity is confirmed by the guard checking a photo ID against the
  screen; the system does not store photographs or ID documents.
- On Render's free tier the SQLite file is reset when the service redeploys
  unless a persistent disk is attached (SETUP.md explains how).

## Possible extensions
